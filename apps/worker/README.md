# apps/worker

Background processing layer: storage scanning, intelligence/recommendation jobs, and execution-engine tasks that must not block the request/response cycle of `apps/backend`.

Event/queue-driven — consumes jobs enqueued by the backend, never receives direct HTTP traffic. Python + Celery, broker/result backend on Redis (ADR-005, ADR-012).

Phase 1 only proved the queue round-trip via `worker.health.ping`. Phase 4 adds the first real business job: `worker.scan.run` (`worker/tasks/scan.py`), which invokes `ScannerService` (`worker/scanner/scan_service.py`) — a provider-agnostic, read-only traversal of every storage source a connector exposes, upserting `Folder`/`File` inventory rows via `packages/shared`'s DB layer. Retries up to 5 times (30s backoff) on transient Google API failures; supports cooperative cancellation via `ScanJob.cancel_requested`. See [`Docs/phases/PHASE_04_STORAGE_INTELLIGENCE.md`](../../Docs/phases/PHASE_04_STORAGE_INTELLIGENCE.md) and [ADR-016](../../Docs/03_ARCHITECTURE_DECISIONS.md#adr-016-storage-scanner-design--two-pass-hierarchy-resolution-cooperative-cancellation-job-level-retry) for the traversal/hierarchy-resolution/retry design, and [ADR-015](../../Docs/03_ARCHITECTURE_DECISIONS.md#adr-015-extract-dbsecurityconnector-code-from-appsbackend-into-packagesshared-ahead-of-phase-4) for why the worker can now import `vault_shared.db.*` at all.

Phase 5 adds the Knowledge Engine (`worker/enrichment/`): `worker.enrichment.run` (`worker/tasks/enrichment.py`) invokes `EnrichmentService` (`enrichment_service.py`), which runs ten deterministic per-file processors (`processors.py`) — extension/MIME/classification/folder-context/naming-pattern/ownership/sharing/language — plus a real Content Extraction Framework (`extraction.py`, PDF/DOCX/XLSX/PPTX/TXT/Markdown, and Google-native Docs/Sheets/Slides via Drive's `export` endpoint) and a bounded cross-file relationship pass (`relationships.py` — sequential versions, exact-checksum duplicate candidates, shared ownership). Auto-triggered after every successful scan (`worker/tasks/scan.py`'s completion chain) or manually via the backend's `/v1/connectors/{id}/enrichment`. Same job-level retry/cancellation shape as the scanner, plus per-file and per-processor failure isolation (one file's or one processor's failure never stops the rest of the job). See [ADR-017](../../Docs/03_ARCHITECTURE_DECISIONS.md#adr-017-knowledge-engine-phase-5--deterministic-first-pipeline-content-extraction-and-scanenrichment-chaining).

Phase 6 adds the Embedding Engine (`worker/embedding/`): `worker.embedding.run` (`worker/tasks/embedding.py`) invokes `EmbeddingService` (`embedding_service.py`), which embeds every file with successfully extracted text via `vault_shared.ai_gateway.get_ai_gateway()`'s configured provider (currently `LocalEmbeddingProvider` — free, offline, gensim + pretrained GloVe word vectors, no wheel-compatible transformer available on this platform). The "pending" query treats a file as needing (re-)embedding if it has no stored vector yet, was re-extracted since its last embedding, *or* its stored vector's `model_name`/`model_version` no longer matches the currently-configured provider — and the per-file skip check mirrors that exact condition (content hash *and* model identity must both match to skip), not content hash alone. Auto-triggered after every successful enrichment (`worker/tasks/enrichment.py`'s completion chain) or manually via the backend's `/v1/connectors/{id}/embedding`. Unlike the Scanner/Knowledge Engine, this service has **no job-level retry** — the local embedding provider has no external-connectivity failure mode to retry around — but keeps the same per-file failure isolation and cooperative-cancellation shape. See [ADR-018](../../Docs/03_ARCHITECTURE_DECISIONS.md#adr-018-ai-intelligence-engine-phase-6--ai-gateway-abstraction-local-first-embeddings-mean-centered-similarity-and-a-stubbed-completion-provider).

Phase 7 adds the Recommendation Engine (`worker/recommendation/`): `worker.recommendation.run` (`worker/tasks/recommendation.py`) invokes `RecommendationService` (`recommendation_service.py`), the first job in this codebase scoped to an *organization* rather than a connector — it pulls an org's entire file/metadata/classification/relationship/embedding state in one pass (`FileRepository.list_for_organization_with_details` and friends), evaluates 11 deterministic rules (`rules.py`) across storage/knowledge/security/collaboration/productivity and 2 insight generators (`insights.py`), scores priority via an explainable weighted sum (`priority.py`), and persists recomputable `Recommendation` rows (a rule that stops firing gets its prior recommendation marked `RESOLVED`, never deleted) plus one append-only `DashboardSnapshot`. Auto-triggered after every successful embedding run (`worker/tasks/embedding.py`'s completion chain, resolving the connector back to its organization) or manually via the backend's `/v1/recommendations/refresh`. No job-level retry or cooperative cancellation — a single fast deterministic pass over already-stored data has nothing to retry around or interrupt mid-flight. Zero `AIGateway` calls this phase — see [ADR-019](../../Docs/03_ARCHITECTURE_DECISIONS.md#adr-019-recommendation-engine-phase-7--organization-scoped-jobs-aggregate-not-per-item-recommendations-and-a-100-deterministic-rule-set).

Phase 8 adds the Execution Engine (`worker/execution/`): `worker.execution.run` (`worker/tasks/execution.py`) invokes `ExecutionService` (`execution_service.py`) — **the only module in this entire codebase permitted to perform a mutating call against connected storage.** It branches on `ExecutionJob.is_rollback`: forward execution iterates a plan's `ExecutionStep`s, doing a live pre-mutation Drive read (resource-existence/current-state check), committing a `RollbackRecord` *before* the actual mutating call (so a later failure can never leave an unrecoverable real-world change), applying the action (`set_trashed` for archive/remove-duplicate — Drive's own Trash, never `files.delete` — or move/rename/update-metadata), then verifying with a second live read (a verification disagreement is recorded but does not retroactively fail an already-successful step); rollback iterates the plan's `RollbackRecord`s in reverse, restoring each step's captured `pre_state`. Both paths share one status lifecycle, cooperative cancel *and* pause (a first for this codebase — every prior job type had cancel only), per-step failure isolation, and a full execution-specific audit trail (`ExecutionAudit`). Re-validates connector permissions defense-in-depth on every run, since real time passes between a human's approval and this job actually executing. Never auto-triggered — every run starts from `apps/backend`'s `ApprovalService.decide` (a human's `approve`) or `ExecutionJobService.trigger_rollback`, per the Core Philosophy's "no shortcuts." No Celery retry policy — a partially-applied mutating action retried blind is a correctness risk this phase declines to take. See [ADR-020](../../Docs/03_ARCHITECTURE_DECISIONS.md#adr-020-execution-engine-phase-8--drive-trash-instead-of-deletion-org-scoped-plans-reusing-the-jobrollback-machinery-and-a-narrow-ruleaction-allowlist).

Phase 9 adds the Automation Engine (`worker/workflow/`): `worker.workflow.run` (`worker/tasks/workflow.py`) invokes `WorkflowExecutionService` (`workflow/execution_service.py`), the node-graph execution engine — it walks a published `WorkflowVersion`'s nodes one at a time (trigger, condition, decision, ai_evaluation, approval, execute_action, delay, notification, end), persisting a `WorkflowNodeExecution` per node and the graph's live position/context on `WorkflowExecution` after every step, so a crashed or cancelled run resumes from exactly where it left off rather than restarting. An `APPROVAL` or `DELAY` node returns a `_WAITING` sentinel that pauses the whole execution (never an in-process `sleep()` — a delay re-enqueues itself via a Celery countdown); an `EXECUTE_ACTION` node resolves a published `WorkflowPolicy` against the target recommendation and either skips, pauses for human approval, or auto-executes — an auto-executed action still calls the same `ExecutionPlanService`/`ApprovalService` (now promoted to `packages/shared/vault_shared/execution/` so this worker can call them directly) that a human's approval click would, producing an identical `ApprovalDecision`/`ExecutionJob`/audit trail attributed to the policy instead of a person, per the founder's explicit "policy-gated auto-execution" choice — automation is a second kind of approver, never a bypass. `worker.scheduler.sweep` (`worker/tasks/scheduler.py`, a fixed Celery Beat entry every 60s) invokes `SchedulerService.run_due()`, which atomically claims due `SchedulerJob` rows (`UPDATE ... RETURNING`, so two concurrent sweeps can never double-fire the same trigger), fires a `WorkflowExecution` per due trigger, and always recomputes the next `croniter` occurrence regardless of whether firing succeeded — a claimed row is never silently orphaned. Event triggers are fired via `vault_shared.workflow_events.fire_workflow_event()`, called from four real completion hooks in this app (`tasks/scan.py`, `tasks/enrichment.py`, `tasks/recommendation.py`) plus one in the backend (connector reconnect) — three of the seven named event types (`file_added`/`file_updated`/`storage_threshold_exceeded`) are modeled but have no real firing hook yet, documented explicitly rather than left silent. In-app notifications are dispatched for real via `NotificationDispatcher`; the email channel is fully built (delivery-status tracking, retries) but runs against a `StubEmailProvider` that only logs — no real email is ever sent, the founder's explicit choice this phase. See [ADR-021](../../Docs/03_ARCHITECTURE_DECISIONS.md#adr-021-automation-engine-phase-9--policies-as-a-second-kind-of-approver-promoting-execution-engine-services-to-packagesshared-and-a-db-polled-scheduler).

## Local development

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
celery -A worker.celery_app worker --loglevel=info
```

Requires `REDIS_URL` (see repo-root `.env.example`).
